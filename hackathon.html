The idea

You start with a short campaign brief: what you want to say, who it's for and when it needs to go out. A team of AI agents turns it into posts ready to publish — they write the text, generate photos and video, adapt each piece to the account and platform, and schedule everything on a calendar.

When a post's time comes, the studio publishes it automatically from a real phone. It opens the app, uploads the media, fills in the caption and posts, with nobody touching the phone.

People make the decisions that matter. A human approves the plan, and a human approves the final content. After that, publishing is automated — and the studio checks that every post actually went live.

04

How it actually works

You don't build device control, you don't log into anything, and you don't stand up models. Two concepts are worth understanding before you start.

4.1 The phone layer

One phone per team, addressed by a device ID, authenticated with your team key. Input reaches the phone as Bluetooth keyboard and mouse events — indistinguishable from a person typing. Observation comes back over a separate channel: screenshots and device state.

Nothing is ever installed on the phone. You get a closed loop without the input path looking automated.

You can Roughly
Type, press keys POST …/type · …/key
Tap a named target POST …/tap · {target}
Move, click, scroll POST …/mouse/*
Screenshot, geometry, rotation GET …/screenshot · …/geometry
Open or stop an app POST …/app-start · …/app-stop
Transfer media to the phone provided

The written API reference handed out at kickoff is authoritative.

4.2 Named targets

Taps do not take coordinates. tap({target: "post-button"}) resolves a name to a pixel box held server-side, then taps a random point inside it.

You never send raw pixels, and the randomisation is deliberate — tapping the identical pixel every run is a detectable signature. Targets for the provided apps are already calibrated.

4.3 The model gateway

One OpenAI-compatible endpoint, one key per team.

Kind Notes
Text — local Effectively free. Prototype here
Text — remote frontier model Billed. Use where quality visibly matters
Image generation Billed per image
Video generation Billed per clip, and slow — budget minutes, not seconds

Each team has a spend cap. The number is given at kickoff. Burn it on Saturday and the paid models stop; the local text models keep working.

The single most important idea in this hackathon

Sending a command is not the same as publishing a post. The write to the phone is fire-and-forget — truth comes from the phone screen or from the platform, never from the fact that your call returned 200.

A post counts as published only when you have proof: a post URL, or a screenshot of it live on the account. Teams that skip this always look fine in rehearsal and fail on stage.

05

Rules and guardrails

Guardrails for the whole build

  • Only approved content is published automatically.
  • The system never sends DMs, follows accounts or switches accounts unless explicitly permitted.
  • No hiding or disguising accounts.

Hard rules

# Rule
R1 Nothing gets installed on a phone. No APK, no accessibility service. Ever
R2 Test accounts only. Never publish from a personal or real brand account
R3 Don't burn the account. No tight posting loops, no rapid-fire retries. A checkpointed account costs you your demo
R4 All model traffic through the provided gateway. Never a vendor endpoint directly. Respect your spend cap
R5 Nothing sensitive in a prompt. The paid models are remote — no credentials, no personal data
R6 Taps go through named targets. No raw fixed coordinates
R7 Every run has a hard timeout and a step budget. An unbounded loop on a logged-in account is the worst failure available
R8 Your device only. One job at a time per phone
R9 All code is written during the event. Open-source libraries and models are fine
R10 Everyone follows the [code of conduct link]

The run record

One JSON object per publishing run. These fields are the minimum.

{
  "run_id": "uuid",
  "goal": "post about the new office coffee machine",
  "account": "test-account-3",
  "started_at": "2026-10-11T09:14:02Z",
  "ended_at":   "2026-10-11T09:15:47Z",
  "outcome": "confirmed",
  "evidence": { "kind": "post_url", "ref": "https://…", "note": "text matched" },
  "steps":  [ { "n": 1, "action": "app-start", "ok": true, "ms": 1840 } ],
  "totals": { "steps": 12, "wall_clock_ms": 105000, "spend": 0.14 }
}
outcome must be one of: confirmed · failed · uncertain

uncertain is not a cop-out — it is the correct answer when you sent the command and could not confirm what happened. A system that only ever says confirmed or failed is lying about one of them, and the judges will look for this.

The decision note is read. Keep it short and make it honest — “we tried X, it didn't work, here's why” scores better than a feature list.
